# Galley voice and product copy

**Understand changes. Review in peace.**

Galley helps teams understand GitHub pull requests and GitLab merge requests with readable documents and code, edits in context, and comments beside the relevant text.

## Voice

Write like a helpful teammate: clear, friendly and specific. Lead with what the reviewer can understand or do, then explain the feature that helps them. Use short sentences and familiar words.

Keep humor small and related to the product. “Your scrollbar gets a breather” is enough. Avoid jokes about tired reviewers, careless approvals, hidden mistakes or privacy. Instructions, errors and permissions should be direct and useful.

Describe the benefit before the visual metaphor. The book-proof origin of Galley's name can explain the brand, but people should not need to understand a “reading room” to understand the product.

## Shared terms

| Use | Meaning |
| --- | --- |
| Review | A GitHub pull request or GitLab merge request |
| Documents | Markdown files shown as readable articles |
| Code files | Supported source and configuration files; enabled in Reading settings → Review |
| Edits in context | Changed words in sentences, table edits in cells, or changed code with nearby lines |
| Comments and replies | Feedback posted to the original GitHub or GitLab review |
| Changed parts / Whole files | The exact Context choices in the reader |
| Marked / Clean | The exact Change marks choices in the reader |
| Viewed | File review progress, saved locally or synced with GitHub when a token is available |

Use actual control labels in help text. Calls to action should say what happens: **Add to Chrome**, **Try the live demo**, **Save token**.

## Claims and expectations

- Promise help understanding changes. Do not claim measured speed, fewer bugs, better approval decisions or customer adoption without evidence.
- Say “no Galley account needed.” Private GitHub repositories need a token, and self-hosted sites need permission.
- Explain that code files are optional. Do not imply every binary or file type is supported.
- Comments go to the existing review. Teammates can participate without Galley.
- Approvals, requests for changes and thread resolution happen on GitHub or GitLab.
- Files render in the browser. Galley has no server or analytics. External images can contact their host when the reviewer chooses to load them.
- Demo comments stay in the browser session. Keep this distinct from posting to a real review.

## Copy examples

| Context | Copy |
| --- | --- |
| Product introduction | Help your team see what changed and how it fits together. |
| Feature | See edits in context. |
| Collaboration | Discuss the change beside the text. |
| Settings | Choose a view that helps you follow the changes. |
| Missing context | Choose Whole files in Reading settings → Review → Context to read this file. |

For errors, explain what happened and the next useful action. Keep drafts and permission details explicit when they affect that action.
